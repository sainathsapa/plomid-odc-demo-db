Reading:
  - 28 separators: 13 large (1,312-1,314 bytes; text-rendered vector index
    keys) and 15 small (14 bytes; PK/staging keys).
  - Fit evolution: 12 large + 15 small = 16,240 <= 16,332 cap (fits); adding
    the 13th large separator = 17,562 > cap, so the split runs.
  - Count midpoint 28/2 = 14 puts 13 large + 1 small into the left half:
    17,234 > 16,332 -> write_node rejects it. The right half is 328 bytes.
  - The leaf split in the same file is byte-aware and carries a comment
    explaining exactly this hazard ("a count-based midpoint can produce a half
    that itself exceeds the page payload"); the internal split still uses
    `separators.len() / 2`.

User-visible failure without instrumentation:

Second finding confirmed from code + lifecycle bench evidence (2026-10-16):
EXPLAIN label disagrees with execution when vector.auto_ann_min_rows is set
below the built-in AUTO_ANN_MIN_ROWS (4096):
  - explain.rs:359-371 applies the session threshold first, then calls
    planner_api::choose_exact_vs_ann, which re-applies its own hard gate
    (`row_count > AUTO_ANN_MIN_ROWS`) at planner_api.rs:151.
  - execution (vector_ann.rs:899-906) applies only the session threshold and
    max_ann_rows; choose_exact_vs_ann is never consulted (grep: only
    explain.rs calls it).
  - Live evidence: lifecycle bench cell hnsw n=2000 with
    SET vector.auto_ann_min_rows = 0 -> EXPLAIN "Vector Exact scan" while
    plomid_vector_stats() deltas show miss=1 builds=1 (ANN executed).
  - Impact: misleading plans for operators who tune the knob down; no wrong
    results. Comment in explain.rs ("the plan can never disagree with the
    run") and vector_ann.rs ("shared with EXPLAIN") are both inaccurate in
    this configuration. Severity P3 (observability).

Containment observed in experiments (release binary, scratch servers):
  - control: auto index dropped before the load -> 8,000 rows dim 128 OK.
  - dim 8 / dim 32 vector indexes at 8,000 rows -> OK (keys too small to mix
    into an oversized count half).
  - explicit HNSW index created AFTER a 2,000-row load (build_bulk path), then
    1,000-row batch insert -> OK; the failure needs enough large separators in
    one internal node.
  - threshold degrades with server history: later runs failed at batch 0 of a
    fresh table on a server that had processed several vector-index tables.
